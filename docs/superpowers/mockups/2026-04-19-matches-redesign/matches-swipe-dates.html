Feasibility — both approaches

  • Code change is local. Only src/components/MatchesTabs.tsx and the slice logic in matches/page.tsx. The applyFilters helper and groupByTournament are untouched — the only variable is which date window feeds them.
  • State shape: replace tab: 'yesterday' | 'today' | 'upcoming' with dateOffset: number (days from today). 0 = Today, -1 = Yesterday, +1 = Tomorrow, +2 = Apr 20, etc. The tab label derivation becomes a tiny helper: offset → label (Yesterday/Today/Tomorrow when ±1 or 0, otherwise weekday abbr).
  • Data caveat. Current scheduledMatches query is .limit(50) ordered by scheduled_at asc. Five days ahead might not fit. Bump to .limit(200) (~= 2 weeks at typical daily volume) or switch to a date-range query keyed on the visible window. Either way, the fetch cost is small.
  • Back-compat. Existing ?tab=live|upcoming|results still maps (today/+1/-1). New ?date=YYYY-MM-DD query param for direct deep-linking to a specific day.
  • Swipe handler. Reuse your existing useSwipeTabs hook — it already does horizontal pan with velocity. The difference: instead of 3 fixed indices, it increments/decrements dateOffset unbounded.

Recommendation

Option B (full date strip) if the primary use case is "show me matches on any specific day" — it matches the user's mental model of a scoreboard calendar and every competitor does it this way.

Option A (rolling window) if the primary use case is "show me today, with yesterday/tomorrow as one-tap neighbours" and rare trips further out — it reads cleaner but buries distant days behind a swipe gesture.

My lean: B. Padel seasons have long gaps between tournament weeks, so a user checking "what's on next week" benefits from seeing all the upcoming days at a glance rather than swiping three times through a window.
