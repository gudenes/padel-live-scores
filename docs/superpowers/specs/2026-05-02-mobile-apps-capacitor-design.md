# Padel Nachos mobile apps (Android + iOS) — design

**Status:** design — pending review
**Date:** 2026-05-02
**Owner:** TBD
**Decision summary:** ship native shells for Android (Play Store) now, iOS (App Store) when ready, both wrapping the same Capacitor configuration around the live web app.

## Goal

Get Padel Nachos onto the Google Play Store with parity for an App Store launch later. A user installing from either store should land in the same UX they get on `padelnachos.com`, with native push notifications, native sharing, deep links from web URLs, and a usable offline state.

## Approach: Capacitor in remote URL mode

The web app stays on Vercel exactly as it is. The native apps are thin Capacitor shells that:

1. Open `https://padelnachos.com` in the system WebView (WKWebView on iOS, Chromium on Android)
2. Inject a JS bridge so the page can call native plugins (push, share, deep links, status bar, splash screen)
3. Forward native events (push tap, deep link arrival, app foreground/background) to the page

The web app handles all rendering, routing, data fetching, and auth. The shell only adds native plugins and store presence.

### Why not bundle the web build into the app?

Next.js 16 with App Router relies on server components, ISR, dynamic API routes, and middleware. A static export would strip the parts that make the app work (per-day match SSR, locale-aware routing, server-side stream resolution). Bundling a snapshot also forces a Play Store review for every content change. Remote URL mode avoids both problems.

### Why not TWA?

A Trusted Web Activity is Android-only. Capacitor with `server.url` set to the production domain gives the same "load the live web app" behaviour while remaining portable to iOS. The cost is one extra layer (Capacitor runtime), which is minor compared to maintaining two wrappers.

### Trade-offs of remote URL mode

- ✅ Auto-updates with every Vercel deploy — no store review
- ✅ Zero divergence between web and app
- ✅ Native plugins available where needed (push, share, deep links)
- ⚠️ Offline support requires a service worker (we need this for Play Store anyway)
- ⚠️ App Store review for "thin web wrappers" can reject — mitigation: native push + deep links + share extension are the legitimacy signals reviewers look for

## Repo layout

**Single repo** — `padel-live-scores` holds everything: the Next.js web app today, the Capacitor config, the `android/` Studio project, the `ios/` Xcode project, Fastlane configs. Cross-cutting changes (e.g., a new push trigger needs a server endpoint AND a native config update) land in one PR with one git history.

| Path | Contents |
|---|---|
| `src/`, `public/`, etc. (existing) | Next.js app, service worker, push subscription endpoint, deep link manifest files |
| `capacitor.config.ts` (new) | Bundle ID, server URL, plugin config |
| `android/` (new, gitignored caches) | Android Studio project — generated by `npx cap add android` |
| `ios/` (new, gitignored DerivedData) | Xcode project — generated by `npx cap add ios` |
| `fastlane/` (new) | iOS + Android build/upload automation |
| `.vercelignore` (updated) | Excludes `android/`, `ios/`, `fastlane/` from web deploys |

Vercel build pipeline is unchanged — `.vercelignore` keeps it ignoring the native folders, so deploy speed is identical to today's. Native builds happen locally (Android Studio / Xcode) for development and via GitHub Actions + Fastlane for store releases.

## Implementation phases

### Phase 1 — PWA hardening (~1.5 days, in `padel-live-scores`)

- Add `serwist` (Workbox-based, Next.js 16 / App Router compatible)
- Precache app shell + manifest + icons + brand SVGs
- Runtime caches:
  - Supabase REST → `staleWhileRevalidate`, 5 min TTL
  - Avatar / logo images → `cacheFirst`, 30 day TTL
  - `/api/match-stats` → `networkFirst` with 3s timeout fallback
- Offline fallback page (chunky brand shell + "you're offline" copy)
- Cached match data displayed with "as of HH:mm" timestamp when offline
- Lighthouse PWA audit must pass installability check

### Phase 2 — Capacitor scaffold (~1 day, new `padel-nachos-app` repo)

- Initialize Capacitor 7 project, pin all plugin versions
- `capacitor.config.ts`:
  - `server.url = 'https://padelnachos.com'`
  - `androidScheme = 'https'`
  - splash screen plugin config (orange chunky polygon, 1.5s max)
- Add Android + iOS platforms
- Verify both build and load production locally on a device

### Phase 3 — Native plugins (~3.5 days)

Plugins to integrate (all official `@capacitor/*`):

- `App` — back button, deep link events  *(included in deep links work below)*
- `StatusBar` — chunky brand dark, light icons  *(~0.25 day)*
- `SplashScreen` — orange polygon, web-app-paint dismissal  *(~0.25 day)*
- `Share` — native share sheet (replaces Web Share API on platforms that lack it)  *(~0.5 day)*
- `PushNotifications` — registration tokens, permission flow, handlers  *(see push section)*

Effort budget: 1 day for the four simple plugins + 1 day for deep links + 1.5 days for push = 3.5 days. Push is the longest-lead item — start the FCM / APNs setup on day one of this phase so the certificate provisioning runs in parallel with the simpler plugin work.

**Push notifications (~1.5 days end-to-end, both platforms)**

- Firebase project for FCM (Android delivery + iOS APNs proxying)
- Apple Developer push certificate, uploaded to Firebase
- New Supabase table `push_subscriptions (user_id, platform, token, locale, created_at)` — one row per device install
- Server endpoint `POST /api/push/register` — called on app start with the device token; upserts into the table
- Server endpoint `POST /api/push/send` — internal, called when a notification should fire (e.g., favourite player goes live, match prediction resolved)
- v1 notification trigger candidates (final set decided in Open Questions):
  - Match by a bookmarked player goes live
  - Match in user's prediction resolves
  - Daily morning digest (recommend defer to v1.1)
- Localized payloads (5 locales) — server generates the title/body using `next-intl`'s `createTranslator` (same pattern as the welcome email)
- iOS APNs cert renewal calendar reminder (1 year)

**Deep links (~1 day)**

- Android App Links: `/.well-known/assetlinks.json` published from `padelnachos.com`, signed with Play upload key SHA-256
- iOS Universal Links: `/.well-known/apple-app-site-association` published from `padelnachos.com`, signed with the app's team ID + bundle ID
- Capacitor `App.addListener('appUrlOpen', ...)` to route incoming URLs to the right page
- Test paths: match detail, tournament detail, player profile

### Phase 4 — Android Play Store submission (~2 days)

- Upload keystore generated, credentials stored in 1Password
- Adaptive icon + splash assets generated from brand SVGs
- Asset link verification confirmed (Bubblewrap-style validation tool)
- Play Console setup ($25 one-time)
- Listing assets: feature graphic 1024×500, 4–8 phone screenshots, 4000-char description, privacy policy URL, data safety questionnaire
- Internal testing track → 1-2 testers
- **Closed testing track for 14 days** (Google requirement for new dev accounts since 2024) — needs 20+ testers across 14 calendar days before production access unlocks
- Production submission

### Phase 5 — iOS App Store submission (~2.5 days, when ready)

- Apple Developer Program ($99/year)
- Xcode signing setup, provisioning profiles
- App icons (every iOS size), launch storyboard
- App Store Connect listing: 6.5"/5.5" screenshots, App Privacy details
- TestFlight build → external review (1-2 days) → public

App Review risks for web wrappers:
- "Insufficient native value" → mitigated by Push, Share, Universal Links being real native integrations
- "WebView-only experience" → same mitigation
- Plan for 1 rejection round (~+1 week calendar)

| 1 | Notification triggers in v1 | Ship two triggers: bookmarked player goes live + prediction resolved. Daily digest deferred to v1.1 once we have retention data. |

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Apple App Review rejects "thin web wrapper" | Push + Share + Universal Links are the strongest legitimacy signals; ship all three. Native back-button handling and offline state add to it. |
| FCM/APNs cert misconfiguration silently drops notifications | Pre-launch checklist: send test push to internal devices on both platforms, verify foreground + background + app-killed states |
| Deep link `appUrlOpen` listener races with React router hydration | Buffer incoming URLs until first React paint, then replay |
| Service worker breaks live data freshness | Auth-gated and live-match endpoints excluded from caching; only static + read-mostly data cached |
| Closed testing 14-day requirement misunderstood | Plan calendar around it — internal testing today, closed testing tomorrow, production 2+ weeks out |
| Native folders inflate Vercel deploy size | `.vercelignore` excludes `android/`, `ios/`, `fastlane/` — deploy speed unchanged |

## Out of scope for v1

- In-app purchases / subscriptions
- Native widgets (iOS Home Screen widget, Android App Widget)
- Watch apps (watchOS, Wear OS)
- iPad-specific layouts (ship portrait-locked iPhone layout, iPad runs in compatibility mode)
- App Store Connect localized listings (ship English-only listing first, add ES/PT/IT/FR after launch)
- Background fetch / sync (push-only for v1)

## Acceptance criteria

A user can:
1. Install Padel Nachos from the Play Store (later: App Store)
2. Open the app and land on the home page with the same UX as the web
3. Receive a push notification when a bookmarked player goes live, tap it, and land on the match page inside the app
4. Tap a `padelnachos.com/match/...` link in any other app and have it open inside Padel Nachos (if installed)
5. Open the app while offline and see the last-loaded matches with an "as of HH:mm" timestamp
6. Toggle each notification trigger off in `/profile/notifications`
